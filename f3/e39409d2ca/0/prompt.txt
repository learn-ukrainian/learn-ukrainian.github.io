## What to produce

A new file `docs/design/monitor-api-router-inventory.md`. For **every** router module
`scripts/api/main.py` mounts via `app.include_router(...)`, one table row / section with:

1. Module path, mount prefix(es), route count, line count.
2. Every module-global root/store constant it reads — from `scripts/api/config.py` (e.g.
   `PROJECT_ROOT`, `LIVE_REPO_ROOT`, `MESSAGE_DB`, dashboard/batch roots) or its own file
   (`_repo_root` / `_db_path` / `_store`-shaped module globals). This is the exact set
   `MonitorContext.roots` / `MonitorContext.stores` (§4.1 of the design doc) must cover — list
   every value you find, do not summarize as "the usual roots."
3. Every OPSEC sweep seam that exists *because of* this router: grep
   `tests/api/opsec_sweep/` for `monkeypatch.setattr(...)` calls that patch a name this router
   defines or imports, and attribute each seam to its router. Sum these per-router counts and
   report the grand total as the seam-count baseline (§7 point 3 of the design doc checks future
   shrinkage against this exact number).
4. A proposed step grouping: routers that share a store/root cluster group together; any module
   over ~800–1,000 lines gets its **own** step (do not fold it into a batch); each of the largest
   routers gets an internal route-group breakdown in its own row if it looks like it needs more
   than one migration PR. Follow the design doc's grouping rules in §5.2 point 4 — do not invent
   different rules.

Also produce a machine-checkable summary: total router-module count, total route count, total
seam count, and a per-step tally that sums to the total module count (the design doc's §5.2
"Full accounting" line is the format to match, e.g. `step 1 (4) + step 2 (1) + ... = N modules`).
