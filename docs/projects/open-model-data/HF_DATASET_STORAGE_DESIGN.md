# Private HF dataset storage design

Version: 0.3.0. Status: PROPOSED under [#10772](https://github.com/learn-ukrainian/learn-ukrainian.github.io/issues/10772). This design needs designated Sol and Opus agreement and proper landing. It proposes future storage, not authorization to create repositories, authenticate, upload, change accounts, buy capacity, or publish. The [engineering standard](../../best-practices/dataset-engineering.md) and [word-card companion](WORD_CARDS_DATASET_ENGINEERING_PLAN.md) supply quality and source prerequisites.

The [conditional contract](WORD_CARDS_DATASET_ENGINEERING_PLAN.md#0-reading-rule), including G04 and G29-G34, preserves this design's release gates. P1-P9 have designated conditional design agreement only; held-out execution and fresh critical exact-head review of all seven candidate paths remain pending. No source, annotation, capacity, access or release prerequisite is satisfied by prose agreement.

## Release target and dataset topology

Target 1 is private research collaboration in a project HF organization with specifically named UNLP researchers proposed for read-only dataset access, conditional on the capability decision below. Names, organization identity, namespace, repository grants and effective entitlement are pending operator-controlled verification. A placeholder is not a real account or an approved access grant. No public or gated-public repository or mirror is part of this target.

The proposed lexical base is standalone, with one private dataset repo, version, README card, DoR and DoD. C2 forms/stress, C3 meanings/relations, C4 phraseology, and opt-in C7 historical contrast are deterministic named configurations of that same pinned base. Keep stable lexeme, homonym, sense and MWE IDs and many-to-many source identities. These configurations are not separately mutable factual stores. Text-level C1 correction pairs, C5 spelling, C6 calques and C9 textbook knowledge retain separate datasets/plans and link card IDs where applicable. This topology is a proposal; existing schema and REVIEW_BUILD constraints remain in force.

| Proposed repo identifier | Content and isolation |
| --- | --- |
| `<verified-project-org>/uk-word-cards` | Private lexical base and version-bound `c2-forms-stress`, `c3-meanings-relations`, `c4-phraseology`, `c7-contrast-opt-in` configurations. Contrast is excluded by default. |
| `<verified-project-org>/uk-c1-correction-pairs`, `uk-c5-spelling`, `uk-c6-calques`, `uk-c9-textbook-knowledge` | Separate private datasets, each with its own plan, card, manifests, version and source dispositions. Prefix every shortened identifier with the verified organization. |
| `<separately-controlled-custody>/uk-word-cards-evaluation` | Logical placeholder only. Gold storage and access must be separate from author access; it need not be HF. Do not create it or disclose protected membership in a training repo. |

Raw private corpus bodies, protected gold membership/answers, secrets, internal artifacts, access details and private logs never enter public repositories or public metadata. Repositories hold only the reviewed release payload and permitted documentation, not a mirror of raw source stores. Private access conditions identify authorized recipients and the permitted collaboration scope for project-controlled confidential material. They do not impose blanket research-only, no-redistribution or no-resale restrictions on upstream licensed material. Per-record and per-field licences, attribution and source rights survive private access and later redistribution. Under [CC BY-NC-SA 4.0 §2(a)(5)(C), §3(b)(3)](https://creativecommons.org/licenses/by-nc-sa/4.0/legalcode.en) and the [corresponding CC BY-SA 4.0 provisions](https://creativecommons.org/licenses/by-sa/4.0/legalcode.en), added terms cannot restrict recipients' licensed rights. Source-specific noncommercial/sharealike conditions still apply. The register's **E6 project dataset licence choice remains an operator decision**; this proposal does not select it or assume that one licence covers mixed fields.

## Access capability decision

[HF organization access documentation](https://huggingface.co/docs/hub/organizations-security), consulted 2026-10-16, states that the organization `read` role covers all organization repositories. Per-repository Resource Groups require Team or Enterprise. Individual PRO status does not supply either that capability or organization capacity. A free organization or an individual's PRO subscription cannot be asserted to implement the proposed source-specific repository grants.

The concrete access proposal is read-only access for each named collaborator only to approved source scopes, no inherited access to protected gold, and a verified private repository boundary. The operator must choose an implementable capability before execution:

| Conditional option for operator review | Required evidence and limit |
| --- | --- |
| Resource Groups in the project organization | Custodian verifies an existing Team/Enterprise entitlement or obtains a separate operator decision about any purchase, then demonstrates repo-specific allowed/denied access including inherited roles. No purchase is proposed as already approved. |
| Separate organizations by approved access scope | Operator approves the concrete namespace/membership topology and its maintenance cost; custodian demonstrates each scope boundary. No organization creation or account change is authorized here. |

Recommend verifying existing entitlement first, then returning the measured capability/cost and scope map for an operator decision. Do not silently choose a paid tier, separate organizations, or organization-wide read grants that defeat least privilege. Owner: operator/custodian with the release owner. Dependency receipt must bind the approved topology, entitlement, intended recipient scopes, effective grants/denials and date before repository creation or transfer. These remain UNKNOWN pending that event; the conditional documentation can be reviewed while execution is blocked.

## Authentication and gold custody

The custodian verifies account entitlement and organization configuration out-of-band and keeps the evidence private. This documentation task performs no authentication or HF operation. Future transfer needs authorized scoped authentication through the custodian mechanism without cache login, and verified namespace, private visibility, recipient scope and least privilege. Never publish account selectors, credentials or their handling details.

Private does not mean isolated. If an author can read an evaluation repo through organization-wide privileges, its private flag does not seal gold. The separate steward controls gold membership, answers, aliases, related source identities, adjudications and access logs. Author and training-repo permissions must confer no access to those protected artifacts. Before a seal is admitted, a separate evaluator verifies both allowed researcher read-only access and denied author gold access, including inherited grants, exports, caches and logs. The author never opens gold to verify denial. A gated dataset governs requests for access; it does not by itself establish private visibility or protected custody. See [HF gated dataset documentation](https://huggingface.co/docs/hub/datasets-gated).

Keep structural replay/held-out, calibration, pilot-certification and final release evaluation audit partitions separate. These audit partitions are not consumer train/test splits. Protected units keep their ordinary accepted/held/withheld release dispositions; do not exclude them merely for audit membership or publish a release complement that reveals it. Protected labels, membership and private selection draw state never accompany the release. A private training-data repo must not embed protected membership in split manifests, digests over individually guessable IDs, filenames or error reports. Gold-related public receipts contain only approved aggregate evidence and an opaque protected-receipt reference. An evaluation steward provides safe results for the exact released artifact, not raw answer files.

## Capacity and overage stop

The [current HF storage documentation](https://huggingface.co/docs/hub/main/storage-limits), consulted on 2026-10-16, lists **1 TB of included private storage for an individual PRO plan**, with pay-as-you-go beyond included capacity. This is plan capacity, not measured headroom. It does not establish an organization's entitlement: organization plans have their own allowances and seats. Actual plan, billing scope, current usage and effective project-organization capacity are UNKNOWN until the operator/custodian verifies them. No paid-plan change is authorized.

Before any upload, the release owner records bytes already retained, all current and previous versions, expected new shards/metadata, source-policy partitions, transient duplicate/version overhead, and a reserve. Proposed reserve is `max(20% of verified included capacity, one complete next release)`, pending approval. Require `current retained bytes + new bytes + overhead + reserve <= verified included capacity`. Do not assume identical revisions cost zero or that local file sizes prove billed storage. Reconcile measured usage after readback. Stop before unapproved paid overage; absence of account telemetry is not capacity approval. Do not delete retained versions to make a budget pass.

## Release contents and reproducibility

Each dataset repository contains a `README.md` dataset card with YAML metadata, a substantive `croissant.json` with core and RAI fields, a build manifest, source/licence/provenance manifests, attribution notices, a changelog, and partitioned data. Gold repositories, if separately authorized, receive their own access-controlled documentation without leaking protected membership elsewhere. [HF cards](https://huggingface.co/docs/hub/datasets-cards) describe the README and metadata convention; [Croissant core](https://docs.mlcommons.org/croissant/docs/croissant-spec.html) and [Croissant-RAI](https://docs.mlcommons.org/croissant/docs/croissant-rai-spec.html) define the metadata vocabularies. Validate pinned versions and retain the validator report and digest; generated metadata does not establish semantic quality. Applicable RAI metadata states synthetic-data status: released facts are authentic-source-extracted, with no model-written Ukrainian.

Use Parquet partitions/shards where adequate for the existing record schema. Freeze field types, stable ordering, partition/configuration definitions, null/withheld/conflict semantics, compression and writer versions, shard boundaries, and normalization policy. Keep source-local literals and lexical identities intact. Choose shard size from measured bytes and current official limits before build, not an invented record total. Store exact row/field counts, per-shard SHA-256, schema version, code/configuration/tool versions and source checksums in the manifest. An independent clean-room build compares those digests on the same frozen inputs. Builders retain the host-only REVIEW_BUILD boundary. The separately ordered uploader safety phase is described below; a release step integrates existing artifacts only after all quality and access gates pass.

The [member ledger and container census](WORD_CARDS_DATASET_ENGINEERING_PLAN.md#2-n1-total-member-disposition-δ) cover the entire release, including every release-level file and projection mapping. Required containers are checked against the independently frozen ledger, pinned schema and rules, never inferred from their own exported children. Unknown members are INCOMPLETE, exported deferred members FAIL, and all deterministic members are recomputed. Report the [E10 interval](WORD_CARDS_DATASET_ENGINEERING_PLAN.md#5-a2-estimands-and-inference) with reserved and development mass over the full release. Remainder-only bounds and resolved-mass points retain their own names and denominators; unresolved facts cannot be exported as accepted facts.

Each exported record and mixed-source field retains source ID, edition/snapshot, locator, subject identity/sense/MWE, licence reference, attribution, extraction/transformation version, disposition and derivation dependencies. A repository-level licence label cannot resolve incompatible field terms. Preserve attested licence evidence and separate source-policy partitions or omit an unauthorized public field with a visible owned disposition, never silently export it under a blanket permissive label. Unresolved public redistribution stays private under the authorized research workflow; internal source-use authorization remains decided.

## Versions, readback, and maintenance

A future release binds `dataset version → tag → exact commit → manifest and shard digests`. Tags are convenient names, not intrinsically immutable: the [official repository guide](https://huggingface.co/docs/huggingface_hub/main/en/guides/repository) documents tag creation and deletion. The release owner retains an append-only archived mapping and an independently controlled copy of the release manifest under approved retention. Consumers pin the commit and verify content digests; if a tag moves, refuse the mismatched release and notify the owner rather than overwrite the archived mapping.

Publish a changelog of input snapshots, code/configuration changes, schema/configuration compatibility, quality evidence and known gaps. Verify authorized readback at the exact commit against digests and expected access. A successful upload proves transport only. Changed data, code, judge selection, prompts, tokenizer, parser or source snapshots invalidate the affected semantic proof and require the corresponding stage gates again.

Source changes or a takedown request trigger dependency tracing, current-access suppression, corrected dispositions and a new release or withdrawal notice. Cover data shards, projections, derivative datasets, caches, mirrors and reimports; suppressions must survive rebuild/rollback. Maintenance and takedown owners are open-model-data pending named assignment before release. The operator/UNLP publication liaison owns source permission follow-up. Immutable historical mappings do not require continued access to withdrawn content. Retain only what approved retention permits; bulk corpus deletion, payload moves and history rewriting require separate operator authorization.

### Conditional withdrawal and body-purge runbook

Ordinary withdrawal or a new release removes current access, but old pinned commits may still expose bodies. The proposed response targets are acknowledgement/scope and current-access suppression within 24 hours of a validated request, and a scoped purge decision within 72 hours. These are proposed service targets pending owner/staffing approval, not measured capacity or promises of automatic deletion. Missed targets go to the operator with exposure and owner recorded.

1. The named takedown owner traces source records to shards, derivatives, mirrors, branches, tags, old commit IDs, PR refs and large-file object IDs. Preserve a private scope/evidence inventory and minimal non-body audit mapping under approved retention. Tell consumers which versions are retired and enforce suppression on rebuild/reimport.
2. For **each destructive event**, present that inventory, the exact repository/ref/object boundary, retained audit evidence, expected loss, response deadline and verification plan to the operator. Obtain separate explicit authorization for that event. Approval of this design is never blanket purge authorization; pending approval leaves historical exposure unresolved.
3. After that authorization, the custodian uses supported [HF history/storage mechanisms](https://huggingface.co/docs/hub/main/storage-limits#how-can-i-free-up-storage-space-in-my-accountorganization): remove affected branch/tag/closed-PR refs, delete affected LFS objects where supported, or super-squash to a clean replacement tip when history removal is required. Super-squash is irreversible; deleting a pointer or only moving a tag does not remove a body. For backends/cached objects not covered by those mechanisms, obtain provider-confirmed purge evidence rather than assert deletion.
4. An independent authorized verifier enumerates remaining refs and tries retired commit/object readback through permitted access paths, including derivatives/mirrors. Record which old refs and bodies are inaccessible and which remain reachable. A private repository or failed anonymous request alone does not prove removal. Bind the replacement version and retired mappings to that evidence.

HF ref changes cannot recall existing local/client copies. The takedown owner records remaining exposure, notifies authorized recipients with requested disposal/confirmation where applicable, and retains unresolved provider/cache/client exposure with owner and next event. Do not claim complete recall. Until named staffing and the operator-reviewed procedure exist, release is blocked. No destructive step is executed by this packet.
