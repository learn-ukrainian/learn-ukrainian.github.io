# Task: #7203 — every dispatch hangs minutes in the runtime-tmp orphan sweep (one PR, two halves)

Read `gh issue view 7203 -R learn-ukrainian/learn-ukrainian.github.io` — it carries the measured
faulthandler traceback and numbers. Summary: `cmd_dispatch` → `_sweep_runtime_tmp_orphans` →
`_runtime_tmp_state_for_lease(lease_name)` globs EVERY `batch_state/tasks/*.json` and `json.loads` each
until it finds the record whose task_id maps to that lease name — once per runtime lease dir. On the
Mac: 25 lease dirs × 2,002 records (4.8 GB; single records up to 39 MB) ≈ 50k full JSON parses per
dispatch → 12+ minutes before a worker even spawns. Reproduced tonight on every dispatch.

## Outcome
`delegate.py dispatch` reaches worker spawn in seconds regardless of how many task records exist. The
orphan sweep still reclaims exactly what it reclaims today (no behaviour change in WHAT is swept), and
future task records stay small enough that a full read is cheap.

## Two halves (both required; the second is the root cause of the record bloat)
1. **Lookup** — the lease name is a deterministic function of the task id (`_runtime_tmp_lease_name`).
   Resolve lease → task id directly (persist the task id in the lease dir at creation, or maintain a
   name index) so the sweep never parses a task record to answer a name question. Keep a bounded,
   clearly-labelled fallback for legacy lease dirs that predate the marker, and make sure that fallback
   cannot regress into the full scan per lease (at most one pass, or an index built once per sweep).
2. **Record bloat** — read-only dispatches embed `read_only_checkout_pre` / `read_only_checkout_post`
   whole-checkout snapshots inside the task record (32–39 MB records). Move those beside the record
   (sidecar file under the task's runtime tmp or `batch_state/tasks/<id>.snapshots/…`) or store a digest
   + path, whichever keeps the existing consumers working. Grep every reader of those keys before
   choosing; list them in the PR body.
