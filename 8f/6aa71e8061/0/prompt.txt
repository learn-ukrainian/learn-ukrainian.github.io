## Blocking: `GET /v1/status/{stream_id}` and `GET /v1/digest/{stream_id}` changed 404 → 500 when the DB file is absent

**Root cause:** `MonitorContext._stores()` (`scripts/api/monitor_context.py`) always constructs a
`SessionStreamStore` — `session_streams_store` is NEVER `None`, whether or not the underlying
SQLite file actually exists on disk. Your migration's `if store is None:` guards
(`session_streams_router.py` — check every occurrence, there are at least 3) are therefore dead
code that never fires.

Before your migration, `_store()` explicitly checked `db_path.is_file()` and raised
`FileNotFoundError` if not, which `session_stream_status`/`session_stream_digest`'s
`except (NotFoundError, FileNotFoundError)` caught and turned into a clean 404. Now, a missing
file surfaces only when something actually tries to read from the store — `SessionStreamDatabase`
(`agents_extensions/shared/session_streams/db.py:129`) raises `SessionStreamDatabaseError` (a
`RuntimeError` subclass) in that case, which nothing in the router catches, so it falls through to
FastAPI's global exception handler as an uncaught 500.

**Fix — pick one, don't invent a third mechanism:**

Option A (closer to the original contract): before calling into the store in
`session_stream_status`/`session_stream_digest`/the drift route, explicitly check
`ctx.roots.session_streams_db_path.is_file()` and raise the same `NotFoundError`/404 path the
route already has, mirroring the pre-migration `_store()` check exactly — just reading the path
from `ctx` instead of a module global.

Option B: add `SessionStreamDatabaseError` to the `except (NotFoundError, FileNotFoundError, ...)`
tuple in the routes that need a 404 on a missing DB — but only if you can confirm
`SessionStreamDatabaseError` is ONLY ever raised for the missing-file case in the paths these
routes exercise (grok's review notes it's also raised for other conditions — WAL mode, foreign
keys, schema version mismatches — which should NOT become a silent 404; read
`agents_extensions/shared/session_streams/db.py` in full before choosing this option, since a
blanket catch would hide a real corruption/schema problem behind a misleading 404).

**Whichever you choose:** the `if store is None:` dead-code guards must go — either become a real
check (Option A folds the file-existence check into what was previously a no-op) or get deleted
entirely if the exception-based approach (Option B) makes them redundant. Don't leave dead code
that looks like it does something.

**Also check the `/v1/drift` route** (grok's finding 2) — same missing-DB path, currently an
unhandled 500 both before and after your migration (so not a regression, but worth fixing to the
same 404 contract while you're in this file, for consistency — driver's call whether to include
this in the same PR or note it as a known follow-up; either is acceptable, just be explicit about
which you did).
